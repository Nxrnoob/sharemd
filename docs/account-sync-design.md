# Optional Account Sync — Design

**Status: parked. No code written.** Kept as a record of a direction considered
and not taken.

What changed the calculus: folder shares (`/b/<id>`) now cover the "send someone
many docs as one link" case without any identity system, and the capability-token
model means no part of sharing needs to know who anyone is. That removed most of
the pressure this design was answering. The cross-device library sync it
envisions is still unsolved, still real, and still worth doing if someone wants
it — but it is a convenience, not a foundation, and building it before the
caps below is understood would be the wrong order.

Read the Decision section below on its own terms; the design is sound, the
timing is not.

## Decision

Keep anonymous sharing exactly as it is. Add an **optional** account whose only
purchase is cross-device sync of the user's library. Signup is a suggestion, never a gate.

This is deliberately *not* "add accounts and require login". The capability-token
model survives verbatim and anonymous users never touch the account system.

The key idea is **claim-time ownership transfer**, which is what makes this cheap
and safe. See "Claim handshake" below.

## Why not the alternatives

**Syncing delete tokens to the server** — the obvious way to get cross-device
delete. Rejected: the server would hold a capability over every doc the user has
ever shared. A database leak becomes mass edit/delete. Client-side encryption
doesn't rescue it — Web Crypto has no scrypt or Argon2id, only PBKDF2, which
forces a user-supplied password as key material and rules out passwordless sign-in.
Claim-time transfer removes the need for the token to ever be stored.

**Better Auth's anonymous/guest plugin** — creates a real user row for every
anonymous sharer. That is PII we don't want, at scale, for users who never asked
for anything. It also duplicates the token model instead of replacing it.

**`documents.owner_id` column** — touches the hot table for a feature that needs
to leave every existing row alone. A side table keeps `documents` untouched, so
the anonymous read path cannot regress.

## Library: Better Auth

Researched 2026-10-14. Settled.

| Option | Status |
| --- | --- |
| **Better Auth** | Active. Vercel acquired it 2026-07-07; MIT. SvelteKit + Drizzle + SQLite adapters. |
| Auth.js | Maintenance mode since early 2026 — security patches only, no features. Its team was absorbed into Better Auth. `@auth/sveltekit` is still flagged experimental. |
| Lucia | Deprecated 2024; now a learning resource, not a library. |

Fit against this repo's constraints:

- `@sveltejs/kit ^2.63.0` — satisfies the `2.20.0` floor that `getRequestEvent`
  (required by the `sveltekitCookies` plugin) needs.
- Drizzle adapter takes `provider: "sqlite"`, which is what both Turso and the
  local `file:` database are.
- Password hashing defaults to scrypt, matching `src/lib/server/password.ts`.
- Needs 4 tables (`user`, `session`, `account`, `verification`), generated by
  its CLI into our Drizzle schema.

Operational notes: `sveltekitCookies` must be the **last** plugin in the array.
`svelteKitHandler` serves `/api/auth/*` but does **not** populate
`event.locals` — session resolution has to be done explicitly in
`hooks.server.ts`. Default sign-in rate limit is 3 requests / 10s.

**Credentials: magic link** via Resend. Free tier is 3,000 emails/month,
100/day, 3 domains — ample here, since this is a prompted opt-in feature for a
small user base. Passwordless matters specifically because it keeps open the door
to client-side key derivation later. Requires a verified sending domain.

## Schema

Additive only. `documents` is not altered. Existing rows are not backfilled or
rewritten. Reversal is `DROP TABLE`.

Better Auth's generated tables, merged into `src/lib/server/db/schema.ts`:

```
user(id, name, email, emailVerified, image, createdAt, updatedAt)
session(id, expiresAt, token, createdAt, updatedAt, ipAddress, userAgent, userId)
account(id, accountId, providerId, userId, accessToken, refreshToken, idToken,
        accessTokenExpiresAt, refreshTokenExpiresAt, scope, password,
        createdAt, updatedAt)
verification(id, identifier, value, expiresAt, createdAt, updatedAt)
```

Application tables:

```
-- Server-side folders. Replaces the purely-local sharemd-folders key.
sync_folders(id, user_id, name, created_at)

-- The synced library. One row per (user, doc). doc_id is NOT unique:
-- a doc may legitimately appear in more than one account's library.
library_docs(user_id, doc_id, title, folder_id NULL, created_at)
  PRIMARY KEY (user_id, doc_id)

-- Claimed ownership: proof that this user proved possession of the doc's
-- delete token. This is what authorises account-based edit/delete.
doc_owners(doc_id PRIMARY KEY, user_id, claimed_at)
```

`doc_owners.doc_id` **is** unique — one doc has at most one owning account.
That is what makes a second claim attempt fail cleanly instead of silently
granting two owners.

Note the deliberate asymmetry: `library_docs` allows many-to-many (filing a doc
into a library is an organisational act, not a transfer of rights), while
`doc_owners` is one-to-one (ownership is exclusive).

## Claim handshake

The client already holds each shared doc's delete token in the local shelf
(`src/lib/shelf.ts`). At signup, it presents those tokens once.

```
POST /api/account/claim
{ "docs": [ { "docId": "...", "token": "..." }, ... ] }

→ for each item: resolveDoc(docId), then verifyDeleteToken(row, token)
→ on success: INSERT OR IGNORE INTO doc_owners (doc_id, user_id, claimed_at)
→ response: { claimed: [...], rejected: [{ docId, reason }] }
```

`verifyDeleteToken` (`src/lib/server/docs.ts:49`) is reused as-is — constant-time
scrypt compare, returns false on a NULL hash. The token is used to prove the
claim and is **never persisted**. After the claim, account-session auth is
sufficient to edit or delete that doc.

Per-item rejection reasons:

| Reason | Meaning |
| --- | --- |
| `unknown` | No such doc (or pre-token doc with NULL hash — indistinguishable, same as today). |
| `bad-token` | Token did not verify. |
| `already-claimed` | `doc_owners` already has a row for this doc under a different user. |

Partial claims are expected and fine. A user with 10 docs who only has tokens for
8 claims 8; the other 2 stay anonymous and claimable later from the device that
holds their tokens.

Two-browser conflict is resolved by the `doc_owners` primary key: first claim
wins, later claims by another account are rejected. A doc cannot be owned twice.

### Cost, and why the batch must be bounded

`verifyPassword` uses `scryptSync` with `N=16384, r=8, p=1`
(`src/lib/server/password.ts:3-6`) — deliberately expensive, roughly 50–100ms
per verification on server-class hardware. Claiming a 100-doc shelf in one
request is therefore 5–10 seconds of synchronous CPU, which is a serverless
timeout risk and a self-inflicted DoS vector.

Constraints on the endpoint:

- Cap the request at **25 items**. Client chunks larger shelves across requests.
- Keep `checkRateLimit` on the route, but with a separate, higher bucket for
  authenticated claims than the anonymous 20/hr limit.
- `scryptSync` is synchronous and blocks the event loop. At 25 items that is
  ~1.5–2.5s of blocked loop, which is still too much for a single Vercel
  instance. Investigate `scrypt`'s async form (`node:crypto/promises`) for this
  route specifically — the anonymous single-doc path is fine as-is and should
  not be touched.

This is the single most implementation-sensitive part of the design and should
be measured before shipping.

## Endpoint changes

The anonymous read path `GET /s/[id]` does not change. At all. This is the
property that makes the feature safe to add.

`DELETE /api/docs/[id]` and `PUT /api/docs/[id]` gain a second authorisation
path:

```
1. existing token path  — verifyDeleteToken(row, token)          (unchanged)
2. new session path     — session user owns doc_id in doc_owners (new)
```

Both continue to return the current indistinguishable 404 for unknown keys and
NULL-hash docs, so no existence oracle is introduced. The token path is checked
first and stays authoritative, which keeps behaviour identical for every existing
caller.

## Threat model

**Database leak.** Attacker gains: user emails, session tokens (Better Auth
stores these hashed), library membership, folder names, doc titles. They do
**not** gain doc delete tokens — those are never stored after claim. They cannot
edit or delete claimed docs without a valid session. Residual risk: metadata
exposure (what you named your docs) and session-token cracking, which is
Better Auth's problem, not ours.

Without claim-time transfer, this same leak would have yielded edit/delete
capability over every doc the user ever shared. That is the entire reason for
the design.

**XSS on an authenticated session.** Full access to that user's library, plus
account-based edit/delete on claimed docs. This is a genuine increase over today,
where an XSS yields only the tokens in that browser's localStorage. Mitigated by
the same CSP and sanitisation already in place; accepted knowingly.

**Claim theft.** Presenting someone else's delete token claims their doc. But
whoever holds that token could already delete the doc outright, so this grants no
new capability — only visibility in a library.

**Enumeration.** No listing endpoint over docs or bundles. `doc_owners` is only
reachable through the claim flow, which requires a valid token for the specific
doc. Account auth endpoints inherit Better Auth's rate limiting.

**Anonymous signup abuse.** Magic-link sign-in is email-costed and rate-limited,
which caps account creation at the email provider's throughput. This is the
reason magic link is preferred over a passwordless-but-free signup that would let
a bot create unlimited accounts.

## Migration

- **Schema** — additive `CREATE TABLE` only. No `ALTER TABLE documents`, no
  backfill. Reverts with `DROP TABLE`.
- **Operational** — migrations are *not* automatic at request time. Prod runs
  `db:migrate` against Turso before deploy (`scripts/migrate.prod.mjs`, run from
  `docker-entrypoint.sh` locally). On Vercel there is no entrypoint, so a missed
  migration means the new route 500s in prod while local dev is fine. This is the
  one real risk in this whole design and it is a process risk, not a data risk.
- **Existing shelf entries** — untouched. Old `{id, token}` pairs keep working
  anonymously. Claiming *consumes* tokens as proof but does not invalidate them;
  the anonymous path continues to work for a claimed doc, so nothing breaks if a
  user never signs in.
- **Existing share links** — untouched. No route changes, no id changes.
- **Client** — old localStorage entries must keep parsing. `normalize` in
  `shelf.ts` already drops malformed rows safely, so any new field is additive.

## Prompt placement

Sign-up is prompted, never required, and never on first share — a signup wall on
a zero-friction tool is how you kill the conversion.

Suggested triggers, in order of strength:
1. After the 3rd share in a session (they've demonstrated the core loop).
2. On returning to `/library` with ≥3 docs filed.
3. From an explicit "Sync across devices" affordance in settings — always
   available, never pushed.

Dismissible, once per session, never blocking. Copy should sell the benefit
("your docs on any device"), never the mechanism ("create an account").

## Sequencing

1. **Export/import** — a signed JSON file of the shelf (ids, titles, tokens,
   folders). Importable on another device. No auth, no server state, no accounts.
   Days, not weeks, and it makes the shelf format forward-compatible with claim.
2. **Better Auth wiring** — magic link, session resolution in `hooks.server.ts`,
   account settings page. Anonymous paths untouched; nothing user-visible yet.
3. **Claim handshake** — the ownership transfer above. This is where the feature
   becomes real.
4. **Server-side folders + synced library page.**
5. **Session-authorised edit/delete.**

Steps 2–5 can ship incrementally; step 1 is independently useful and should not
be blocked on the rest.

**The bundle feature (one link → N docs) is orthogonal and should not be blocked
by any of this.** It reuses the capability model and needs no accounts. If both
are wanted, bundles are the smaller and more self-contained piece.

## Open questions

- Is `scryptSync` → `scrypt` (async) sufficient to make a 25-item claim
  comfortably inside a serverless timeout? Needs measurement, not assumption.
- Should `library_docs.doc_id` be unique per user but allow a doc in multiple
  folders? Folders are single-level by design (`shelf.ts`), so a doc has at most
  one folder — but the schema should still permit the join table later.
- Do we want a "shared with me" concept, or is a doc someone else sent me simply
  not in my library? Currently that would mean an anonymous link with no entry.
- What happens to a claimed doc that the user later wants to un-claim? Probably
  nothing — ownership should be permanent once proven.
